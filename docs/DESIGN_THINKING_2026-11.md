**범위:** 포지셔닝 v7(가벼운 개방형 레이크하우스)의 대상 고객이 DataPond를 알게 된 순간부터 첫 가치를 얻고
구매를 결정하기까지. **근거:** 사용자 인터뷰는 아직 없다. 이 문서의 공감 단계는 기존 조사(`MARKET_REVIEW_2026-10.md`
§5–§8), 라이브 콘솔 페르소나 검증(`PERSONA_REVIEW_2026-11.md`), 우리가 직접 겪은 설치·재구축·운영 기록
(`DEPLOY_SINGLE_NODE.md`, `DISASTER_RECOVERY.md`, 2026-11-06 재구축)에서 추론했다. 그래서 결론은 **검증할 가설**이지
사실이 아니다. 마지막 절이 그 검증 계획이다.

## 1. 공감 (Empathize)

### 1.1 누구인가

시장성 재검토 §6.2의 재정의를 그대로 쓴다: **AWS 이관을 마쳤고 MSP가 관리하는 중견기업.** 직원 300–1,000명,
AWS 월 $1만–5만, 데이터 수백 GB–10 TB, 데이터 인력 1–4명. A형은 Databricks를 소규모로 쓰는 회사(예산이 있다는
신호), B형은 MSP가 Athena·Glue를 조립해 준 회사다.

| 페르소나 | 하는 일 | 원하는 것 | 두려운 것 |
|---|---|---|---|
| **박 팀장** (IT팀장, 결정권자) | AWS 비용과 인력, 벤더 계약 | 다음 달 청구서를 예측할 수 있는 플랫폼 | 또 하나의 종속, 운영할 사람이 없는 시스템 |
| **김 매니저** (데이터 담당, 1–4명 중 1명) | 원본 DB에서 리포트까지 파이프라인 | 원본과 레이크를 한 SQL로, 동기화가 알아서 | 이전 작업이 몇 달 걸리는 것, 깨진 동기화의 새벽 알림 |
| **이 책임** (정보보호) | 개인정보·감사 대응 | 누가 무엇을 봤는지 증적, 주민번호가 레이크에 안 들어가는 것 | AI 과제가 개인정보 심사에서 반려되는 것 |
| **최 SA** (MSP 솔루션 아키텍트, 채널) | 고객마다 데이터 환경 구성 | 고객마다 다시 조립하지 않는 표준 구성 | 구축 후 장애 책임이 MSP로 오는 것 |
| **정 PM** (AI 추진 담당) | 사내 생성형 AI 과제 | 사내 데이터에 안전하게 연결된 챗봇·에이전트 | 데이터 접근 심사 지연 |

### 1.2 공감 지도 — 김 매니저 (가장 자주 제품을 만지는 사람)

| | |
|---|---|
| **말한다** | "Databricks는 좋은데 우리 규모엔 과해요." "Athena 쿼리 비용이 매달 들쭉날쭉해요." |
| **생각한다** | "옮기는 데 몇 달 걸리면 그게 더 비싸다." "내가 휴가 가면 이건 누가 돌리지?" |
| **한다** | Glue 크롤러·Lambda·Athena 쿼리를 손으로 이어 붙인다. 원본 DB를 덤프해 S3로 올린다. |
| **느낀다** | 혼자 플랫폼 전체를 떠안은 부담. 새 도구를 들이는 것 자체에 대한 피로. |

### 1.3 지금의 여정 (B형, Athena·Glue 조립)과 우리가 확인한 마찰

| 단계 | 고객이 겪는 것 | DataPond로 바꿨을 때 오늘 실제로 겪을 것 (우리가 직접 겪은 근거) |
|---|---|---|
| 알게 됨 | MSP 제안, 블로그 | 홍보 자료는 v7로 정리됐지만 **비용 비교·이전 사례가 없다** |
| 시험 설치 | — | `DEPLOY_SINGLE_NODE.md` **762줄, bash 블록 20개**, Terraform + Helm. 재구축에 우리도 **약 1.5시간**과 문서에 없던 막힘 7건(k3s 체크섬, Secret 소유권, CD 권한, S3·시크릿 import, 스냅샷 복원 설정, 첫 Helm 설치 수동, 노드 ID)을 겪었다 |
| 첫 데이터 | 덤프·크롤러 | 샘플 소스는 1클릭. 실제 DB 연결 후 **엔진 재시작 약 1분**, 동기화는 수 초–수십 초. 오래된 대상 테이블과 타입이 안 맞으면 동기화가 멈춘다(라이브에서 `api_events`가 이틀간 실패) |
| 첫 쿼리 | Athena 콘솔 | 레이크 ⋈ 원본 조인 1.2초, 차트 자동 — **가장 강한 순간** |
| 거버넌스 | 거의 없음 | 행 필터·마스킹·감사 있음. 하지만 화면에서 "주민번호가 안 들어갔다"를 한눈에 보여주는 곳이 없다 |
| 운영 | MSP 티켓 | Spot 용량 부족으로 아침 시작 실패(11/10–11), CPU 예약 초과로 배포 실패(11/12) — **운영 지식이 아직 우리 머릿속에 있다** |
| 구매 결정 | 청구서 | **"이게 얼마고, 지금보다 얼마나 싼가"에 답하는 화면이 없다** |

### 1.4 관찰에서 나온 통찰

1. **기술은 증명됐고, 첫 주가 프로젝트다.** 첫 쿼리는 강렬하지만 거기까지 가는 길(설치·연결·타입 문제)이 고객 혼자
   걸을 수 있는 길이 아니다.
2. **구매는 기능이 아니라 두 숫자로 결정된다.** 월 비용의 예측 가능성, 그리고 이전에 드는 시간. 둘 다 지금 제품이
   보여주지 못한다.
3. **실제 사용자는 혼자다.** 데이터 인력 1–4명은 장애를 혼자 맞는다. "잘 돌고 있다"를 증명해 주는 화면이 기능보다
   중요하다.
4. **채널(MSP)이 첫 고객이다.** MSP SA가 고객마다 반복하는 조립을 대신하는 순간 가치가 생긴다. MSP에게 필요한 것은
   기능 목록이 아니라 표준 설치와 장애 책임의 경계다.
5. **개인정보는 차별점인데 보이지 않는다.** 마스킹은 동기화 안에서 조용히 일어나서, 정보보호 담당이 확인할 증거가
   화면에 없다.

## 2. 정의 (Define)

### 2.1 관점 진술 (POV)

> **김 매니저는** 혼자서 원본 DB와 레이크를 한 SQL로 다루는 환경을 **며칠 안에 직접 세우고 계속 돌릴 수 있어야
> 한다.** 몇 달짜리 이전 프로젝트나 운영할 사람이 따로 필요한 플랫폼은 그의 회사에 들어올 수 없기 때문이다.

> **박 팀장은** 도입 전에 **"월 얼마, 지금보다 얼마나 덜"과 "언제든 나갈 수 있다"를 숫자와 절차로 확인해야
> 한다.** 그는 기능이 아니라 비용 예측 가능성과 종속 위험으로 결정하기 때문이다.

### 2.2 How Might We

1. 어떻게 하면 **설치에서 첫 연합 쿼리까지를 한 사람이 한 시간 안에** 끝내게 할 수 있을까?
2. 어떻게 하면 도입 **전에** 고객의 현재 데이터 자산을 보고 **비용과 이전 기간**을 보여줄 수 있을까?
3. 어떻게 하면 혼자 운영하는 데이터 담당이 **"잘 돌고 있다 / 무엇이 깨졌고 무엇을 하면 된다"**를 한 화면에서 알게 할 수 있을까?
4. 어떻게 하면 정보보호 담당이 **개인정보가 레이크에 들어가지 않았다는 증거**를 직접 확인하게 할 수 있을까?
5. 어떻게 하면 MSP가 **고객마다 같은 표준 구성을 반복 설치하고 장애 책임 경계를 명확히** 할 수 있을까?

## 3. 아이디어 (Ideate)

HMW별로 넓게 낸 뒤, 영향(대상 고객의 결정·지속 사용에 미치는 크기)·노력·근거(관찰로 뒷받침되는 정도)로 1–3점을 매겼다.

| # | 아이디어 | HMW | 영향 | 노력(낮을수록 쉬움) | 근거 |
|---|---|---|---|---|---|
| A1 | 원클릭 설치 (CloudFormation/Marketplace, 질문 5개짜리 마법사) | 1, 5 | 3 | 3 | 3 |
| A2 | "첫 주 체크리스트" 콘솔 온보딩: 소스 연결 → 동기화 → 첫 쿼리 → 권한 → 개인정보 확인 | 1 | 3 | 1 | 3 |
| A3 | 설치 사전 점검기 (Spot 용량·쿼터·Bedrock 접근·CPU 예약을 설치 전에 검사) | 1, 3 | 2 | 1 | 3 |
| B1 | **이전 진단 리포트**: Glue/Unity/Delta 인벤토리를 읽기 전용으로 스캔해 테이블 수·크기·형식·예상 이전 기간·월 비용 산출 | 2, 5 | 3 | 2 | 2 |
| B2 | 비용 카드: 이 배포의 실제 월 비용(AWS Cost Explorer 태그) + 쿼리량 대비 Athena/Databricks 환산 | 2 | 3 | 2 | 2 |
| B3 | Delta → Iceberg 변환 도구 | 2 | 2 | 3 | 2 |
| C1 | **운영 상태 한 줄**: "어제 동기화 14/16 성공, 실패 2건 — 원인과 고치는 버튼" | 3 | 3 | 1 | 3 |
| C2 | 동기화 실패 자동 진단 (타입 불일치 → "대상 다시 만들기" 제안) | 3 | 2 | 1 | 3 |
| C3 | 주간 메일 리포트 (정상·실패·비용) | 3 | 2 | 1 | 2 |
| D1 | **개인정보 증적 화면**: 테이블별 마스킹된 컬럼·건수·마지막 동기화, 감사 내보내기 버튼 | 4 | 3 | 1 | 2 |
| D2 | ISMS-P 증빙 템플릿 내보내기 | 4 | 2 | 2 | 1 |
| E1 | MSP 콘솔: 여러 고객 배포의 상태·버전 한곳에 | 5 | 2 | 3 | 1 |
| E2 | 표준 구성 + 책임 경계 문서 (MSP용 운영 계약 초안) | 5 | 2 | 1 | 2 |

**고른 것** — 영향 3에 노력이 낮거나 근거가 강한 묶음:
- **콘셉트 1 "한 시간 레이크하우스"** = A1 + A2 + A3
- **콘셉트 2 "이전 진단 리포트"** = B1 + B2
- **콘셉트 3 "혼자 운영해도 되는 콘솔"** = C1 + C2 + D1

B3(Delta 변환)와 E1(MSP 콘솔)은 영향은 있지만 노력이 크고 근거가 약해 검증 뒤로 미룬다.

## 7. 이 문서가 하지 않은 것
