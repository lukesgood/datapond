# 온톨로지·GraphRAG 적용 필요성 검토

> 작성: 2026-10-15 · 상태: **결정 기록** · 근거: `ONTOLOGY_FEASIBILITY_REPORT.md`(자체 실험 5종),
> `CONCEPT_RECONFIRMATION.md` §5(수요 게이트), `POSITIONING_REVIEW.md` §3.4, RFI-260916 내부참조(저장소 밖 보관).
> 계기: 외부 대화에서 "DataPond에 시맨틱 레이어·온톨로지·GraphRAG를 붙이자"는 제안을 검토했다.
> 그 대화는 v3.0 OSS 레이크하우스 시절의 DataPond를 전제로 했다. 현재 v6.0은 governed 데이터 도구 서버이고,
> pgvector RAG는 핵심 기능으로 출시돼 있으며, 온톨로지 0단계(개념·별칭 저장소, `app/api/ontology.py`)가 있다.

## 결론

| 항목 | 지금 필요한가 | 이유 |
|---|---|---|
| 온톨로지 개념 계층 (개념·별칭·PII 태그) | 일부 필요. 0단계를 다듬는 정도 | 효과가 확인된 곳이 개념 단위 거버넌스와 전문용어 검색으로 좁다 |
| SQL 의미 정의 (지표·조인 경로·용어집) | **필요. 착수** | 정형 데이터용 온톨로지의 실용판. 누가 물어도 같은 SQL과 같은 답이 나와야 governed SQL이 된다 |
| 온톨로지 Phase 1 (엔티티 그래프·관계) | 근거 없음 | 관계 추출이 실험에서 가장 약했고(0.22–0.78), 관계를 묻는 수요도 확인되지 않았다 |
| GraphRAG | 근거 없음, 거버넌스 위험 | 호출자별 접근 통제와 구조적으로 충돌한다 (아래) |

## 질문 유형과 맞는 해법

| 질문 유형 | 예 | 해법 |
|---|---|---|
| 한 곳에 답이 있는 사실 질문 | "연차 이월 규정은?" | 현재 벡터 RAG와 인용. 품질은 W7b·W7c로 보강 (`DATA_RESIDENCY_BACKLOG.md`) |
| 테이블 지표 질문 | "지난달 매출은?" | SQL 의미 정의. 지금 `/ai/sql`은 스키마 설명만 받는다 |
| 전문용어·코드 질문 | 질병코드, 부품번호 | 개념·별칭 확장(실험 4에서 recall@1 +0.25)과 하이브리드 검색 W7b |
| 여러 문서를 엮는 질문, 전체를 묻는 질문 | "지난 분기 장애의 공통 원인은?" | GraphRAG의 영역. 다만 더 싼 대안이 먼저다 |

## 근거

- **고객 요구:** RFI-260916에는 온톨로지·지식 그래프를 요구하는 항목이 없다. 요구 항목은 PII 차단, 감사, 온프레미스 LLM, 장애 시 전환이다.
- **자체 실험:**
  - 개념·별칭 추출은 자동화할 수 있다(재현율 0.75–1.00).
  - 관계 추출은 모든 분야에서 가장 약했고, 실행할 때마다 편차가 컸다.
  - 일반 동의어 검색 개선 효과는 0이었고, 전문용어에서만 효과가 있었다.
- **실험의 공백:** 영문 합성 코퍼스 3–6건으로 실험했다. 한국어와 실제 규모는 검증하지 않았다.
- **비용:** GraphRAG는 색인할 때 청크마다 LLM 호출이 필요하다. 그래서 호출자별 예산, 데이터 레지던시(리전 밖 처리), 온프레미스 GPU 용량 문제를 모두 키운다.

## GraphRAG와 거버넌스의 충돌

DataPond의 차별점은 어떤 호출자가 어떤 컬렉션·청크·행을 읽을 수 있는지를 데이터 계층에서 통제하는 것이다.

- **엔티티 병합:** 여러 문서의 사실을 한 노드로 합친다. 공개 문서와 제한 문서의 사실이 같은 노드에 섞인다.
- **커뮤니티 요약:** 여러 청크를 미리 LLM으로 요약해 저장한다. 요약에 권한 없는 청크의 내용이 들어가면, 청크 단위 caller filter(`app/chunk_access.py`)나 검색 결과 PII 재마스킹으로 다시 걸러낼 수 없다.
- **해결 비용:** 노드, 관계, 요약마다 출처 청크를 추적해 호출자 권한으로 거르고, 권한 범위별로 요약을 따로 만들어야 한다. 구축 비용이 몇 배가 된다.

## 진행할 것

1. **SQL 의미 정의:** 지표·조인 경로·용어집을 정의해 `/ai/sql`에 넣고, 쓴 정의를 감사 기록에 남기며, MCP 읽기 도구로도 노출한다. 그래프와 추론은 넣지 않는다. 설계 문서로 진행한다.
2. **0단계 개념 계층 보강:**
   - 개념 매칭이 덜 발동하는 문제(실험 4)를 고치고, 한국어 별칭으로 검증한다.
   - 전문용어 질문에는 W7b 하이브리드 검색과 함께 적용한다.
   - SQL 의미 정의의 용어집과 개념 저장소는 하나로 합친다.
3. **GraphRAG 수요 측정:** `tool_call_log`의 `ai.rag` 기록 가운데 답을 찾지 못했거나 인용이 적은 질문을 모아, 여러 문서를 엮는 질문과 전체를 묻는 질문의 비율을 본다.

## 다시 검토할 조건

- **GraphRAG:** 3번의 측정에서 여러 문서를 엮는 질문과 전체를 묻는 질문이 의미 있는 비율로 나올 때 다시 검토한다. 그때도 순서는 다음과 같다.
  1. 권한 범위 안에서 동작하는 싼 대안을 먼저 시도한다. 질문을 하위 검색 여러 개로 나누는 방식(multi-query)과 검색 결과를 map-reduce로 요약하는 방식이다.
  2. 그래도 부족하면 권한을 인식하는 그래프 설계를 전제로 GraphRAG를 검토한다.
- **온톨로지 Phase 1:** `CONCEPT_RECONFIRMATION.md` §5 기준을 유지한다. 디자인 파트너가 관계·개념 수준의 질의를 실제로 요구할 때 착수한다.
- **하지 않는 것:** Cube·MetricFlow 애드온은 애드온을 늘리지 않는다는 결정과 충돌한다. 고객이 이미 쓰고 있으면 정의를 가져오는 대상으로만 둔다. Ontop·Jena(OWL/SPARQL)는 표준 어휘를 가진 의료 고객이 생길 때만 검토하고, Semantica는 관찰만 한다.
